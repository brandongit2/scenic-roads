How it would get to the page one transport for everything live

Nothing live goes through the NAS

The NAS takes 20–55 small-file creates a second and listings take seconds under load. Live data stays in each agent's memory and is read over HTTP, like the worker page already reads its own Mac.

/work/live on every Mac

One JSON answer for a chosen range (or an event stream for what follows): rates, vitals, transfer events, the jobs' current target and phase. The page asks each Mac in the pool directly; the heartbeat already lists their addresses.

The coarse feeds stay as they are

status.json, view.json, forecast-input and the history keep their cadence and remain the truth; the live charts read the history store below, which is for the eye: losing it loses no build work.

History that outlives the page

Each agent writes its samples to a small file on its own Mac's disk (never the NAS): every second for the last hour, a 10 s summary for a day, a 1 min summary for 72 h, each summary keeping the low, mean and high so spikes survive. About 4 MB a Mac, flushed once a minute, so a page opened later, or an agent restarted, still has the history. A Mac asleep or off shows as a gap.

Cheapest first

1. the map and per-target table from fields already on the wire. 2. byte counters at the three choke points plus the 1 s sampler. 3. the probe and the proxy's counters into the status. 4. live phases. 5. the Synology's own view, if an account is made for it.
